# 评测与对照实验方案

目的：给 agent-lite 的工程改进提供可复现数据，回答“在固定模型和预算下，这个 agent 更可靠、更准确或更省成本了吗”。不以自建题排名推导通用智能或生产安全结论。

## 1. 测什么，如何区分

| 维度 | 题目/协议 | 主指标 | 可说的结论 |
| --- | --- | --- | --- |
| 精确交付 | A01、A02、A03 | 全题通过率；保护文件违规数 | 这组精确任务的完成能力 |
| 代码行为正确 | C01、C02 | 隐藏用例全通过的任务比例 | 这组协议下的代码修复/实现能力 |
| 持续工作 | L01 normal | 全阶段通过率；首次失败阶段；最长成功阶段前缀 | 多阶段持续完成能力 |
| 会话恢复 | L01 resume | 规定重启后的全阶段通过率 | agent 会话恢复后的端到端表现 |
| 压缩后持续工作 | L01 compaction | 实际压缩样本中的后续阶段通过率 | 允许持久笔记/检索条件下的压缩工作流表现 |
| 效率 | 同题同模型同预算 | 成功任务耗时中位数/P90；每个成功任务的总成本 | 在该任务分布上的效率权衡 |

主指标是 `autonomous_success`，不是“说自己完成”“工具调用多”“测试跑过”。准确和长任务分别报告，不把几个维度相加成一个看似精确的总分。`partial_score` 仅用于定位失败，不取代全题通过率。

## 2. 三步实验规模

### 第一步：检查链路

运行 `python selftest.py`，然后用任一实际 agent 在 smoke 每题跑 1 次，共 6 次。使用开发种子 17。检查题面是否充分、环境能否跑 Python、CLI 是否支持长输入、日志能否归档。这里可修出题错误，但更新版本后旧结果失效。

自测包含参考解，但被测 agent 不应看到。自测跑出的“通过”绝不能算 agent 成绩。API 密钥只交被测 agent 运行时，不写进题包或报告。

### 第二步：小预算试验

6 题 × 标准档 × 1 个开发种子 29 × 2 次独立重复 × 2 个候选配置 = **24 次**。

先确认失败分布和真实耗时：是否存在全部秒过/全部不可解的题，是否有读取截断、是否真实产生压缩，模型/后端是否有独立于任务的错误。根据试跑一次性确定正式时限和资源；随后锁定，不能看到某组失败后再单独延长。

### 第三步：固定保留集

6 题 × 标准档 × 3 个保留种子 × 3 次独立重复 = **每个配置 54 次**；2 个配置共 **108 次**。

建议保留种子 17017、17029、17043，试跑阶段不要生成/阅读其数据和答案。填好 `templates/experiment.json` 并归档 SHA-256。这些只是同模板新数据，不是新题族，也不防止模型从已公开规范中学习；报告必须说明。

长任务专项独立：L01 long × 相同 3 种子 × 3 重复 × normal/resume/compaction 三协议 = **27 次/配置**。只有确实发生对应事件的样本才能计入专项条件成功；应同时报告未触发次数，不能悄悄换样本直到触发。

先做第二步再决定是否执行全部第三步。不要为了简历立刻消耗大量 API 额度；本套工具不自动发起调用。

## 3. 预算和环境固定

初始试跑建议：smoke 10 分钟；standard 30 分钟；long 60 分钟。都只是初始预算建议，不是预期完成时间。标准档可先设累计 billed tokens 120,000、工具调用 200 的辅助上限；长档先设 240,000 和 400，按试跑成本一次性调整后冻结。

到达任一预算就停止，剩余产物照样评分，状态 timeout。计费 token 包括所有模型轮次、摘要调用和可计费重试，不能只取最后一次请求。`eval.py` 不执行这些停止动作；由实验员或额外的进程监督器实施。报告若未实施 token/工具上限，明确填写“仅墙钟预算”。

必须固定并记录：

- agent 代码提交、题包版本、初始 fixture_sha256、题目/种子/重复号、配置分组。
- provider、模型精确 ID、端点、采样参数或“provider 默认”；不要把 alias 当固定快照保证。
- 系统提示词/模式、工具列表、权限策略、网络策略、Python 与 OS、沙箱镜像摘要。
- context window、压缩阈值、保留比例、摘要目标长度、fallback、工具输出长度与全文保存规则。
- 时间、token/费用/工具上限、重试上限、起止规则、是否允许持久笔记、外部检索和缓存。

每次重复新建 workspace 和 agent 会话；不能恢复上一次重复来增加成功率。只有 resume 协议在同一次 attempt 内恢复同一会话。后台其他任务、网络和 provider 负载会影响耗时，应随机交错 A/B 顺序，保存调度种子。

## 4. 对照组，隔离工程贡献

首先选一个问题做 A/B，不要同时改模型、提示词、工具和压缩策略。

| 对照 | 固定项 | 唯一变化 | 验证条件 |
| --- | --- | --- | --- |
| agent-lite 修复前/后 | 同模型、同工具接口、同预算/环境/数据 | 一个明确代码改动或提交区间 | 相同题/种子/重复号一一配对 |
| 自动压缩开/关 | 同模型物理窗口、相同其他设置 | 本地压缩功能；关组可用 `--context-window 0` | 记录实际超窗/压缩，不能把禁用计量当扩大模型窗口 |
| 新/旧工具输出策略 | 相同模型、截断上限等非目标参数 | 全文保留/截断提示策略 | 只有观察到实际截断才能分析该机制 |
| 不重启/规定重启 | 同版本、模型、数据、规则 | 阶段间退出并恢复 | 保存前后 session ID、进程/日志时间戳 |
| agent-lite/其他 agent | 相同模型若支持、同题面与预算 | 完整 agent 产品 | 无法固定模型时只能比较“系统组合”，不能归因于 harness |

主推简历实验是“同模型下，某个已实现机制改进带来的变化”。外部 agent 的默认提示词、服务端工具和不可见缓存不同，应逐项披露可控程度。

## 5. L01 的严格操作时间线

1. 生成并 start，发送当前 PROMPT；输入只含阶段 1。
2. agent 结束本轮后，立即 checkpoint，冻结原字节，不向 agent 反馈对错。
3. 原样发送 `next_prompt.txt`，继续当前会话，不添加鼓励、提示或修复建议。
4. 阶段 3 的消息发布新单位规则。以后只有新批次提示，不重复提醒乘数。
5. normal：继续；resume：标准档在冻结阶段 4 后退出，long 在阶段 8 后退出。保存日志并以同一 session 恢复，随后发送下一阶段提示。不要重发整个旧对话或人工总结。
6. compaction：使用事先固定的较小本地窗口（试跑可从 16,000、阈值 0.8、保留 0.16 开始），保留实际成功压缩事件。若做 `/compact` 强制实验，必须预先规定触发边界并另命名配置，不能与自动压缩混报。
7. 每阶段都冻结，包括最后一阶段。完成后停止 agent 写入，再 finish 和 grade。

允许 agent 自己在 scratch 写状态/笔记、重读历史文件；不给额外隐藏数据。这是实际使用场景，也意味着结果只能解释为“上下文管理+磁盘记忆+检索+模型”的整体表现。若要纯上下文保持实验，另建不可检索历史条件，不要临时删除文件来改变本套题的任务定义。

`checkpoint` 只是复制冻结，不是权限系统；正式盲测要让 agent 无法写 private、run.json 和 results。不能在当前公开源码的根目录直接给一个全权限 agent 做题，又声称答案不可访问。

## 6. 记录与审计

每次保留：原始输入快照和初始哈希、agent 完整事件日志、最终 workspace、阶段快照、run.json、grade.json、telemetry.json、会话 ID、异常日志。公开时去掉凭据和非本次实验会话。

推荐中立事件 JSONL 契约，供未来适配器实现（当前控制器不采集此事件流）：

```json
{"at":"2026-09-21T10:00:00Z","type":"model_usage","request_id":"u1","purpose":"main","input_tokens":100,"output_tokens":20}
{"at":"2026-09-21T10:01:00Z","type":"model_usage","request_id":"u2","purpose":"compaction","input_tokens":800,"output_tokens":120}
{"at":"2026-09-21T10:02:00Z","type":"tool_end","call_id":"t1","name":"read","ok":true,"truncated":true}
{"at":"2026-09-21T10:03:00Z","type":"compaction_end","success":true}
{"at":"2026-09-21T10:04:00Z","type":"resume","session_id":"same-session","after_phase":4}
```

以上是格式示意，不是观测数据。实际模型 usage 应在每次请求结束时采集，摘要使用独立 provider 也必须记录；输入计费中缓存命中/未命中按实际供应商价格分类，reasoning 是否含在 completion 中按 usage 口径核对，避免重复计算。

agent-lite 的 `session.usage` 是上下文计量锚点，**不是累计花费**，不能直接当本次总 input_tokens。仅有会话文件时可统计存档工具调用/压缩条目，但不能据此还原所有计费重试；缺失的成本字段保留 null。`compactions` 在 telemetry 中专指成功压缩次数；失败单列。

由实验员填写 `human_interventions`；没有明确观测填 null。自动协议消息、规定重启不算帮助；提示“你漏了一个文件”、帮安装非预设依赖、人工改代码都算帮助并记录内容。修环境后重跑要新建 attempt，保留旧记录。

## 7. 指标和计算口径

设一组固定实验有 N 次计划运行，S 次在预算内无人工帮助并全题通过：

- 单次成功率 = S/N。超时、agent_error 和未交付为失败；基础设施错误也留在主要分母，另报排除已确认 infra_error 的敏感性结果，不能只展示后者。
- 题族宏平均 = 各题族成功率的平均。种子多或测试多的题不能挤占权重。
- 精确通过率 = 对相应 A 题的全题成功率；另报结论/字段正确率用于诊断。字段数多不代表更重要。
- 无违规成功率 = 通过且保护约束不违规。主评分已设置完整性闸门；更强的过程违规需要独立审计。
- 阶段完成率 = 通过的 frozen checkpoint / 计划 checkpoint；首次失败阶段和最长成功前缀揭示“跑了很久但中途已经错”。
- 恢复成功率 = 按协议实际重启且后续阶段全部通过 / 计划恢复实验；附实际重启数、未执行数与从重启到恢复工作耗时。
- 稳定性 `all_success@3` = 同一题+种子三次都成功的组数 / 完整三次组数。不是 pass@3，也不要直接套用未经说明的 pass^k 估计。
- 成功耗时：仅在成功样本中报告中位数/P90，并列失败率和失败耗时；不能删失败后声称整体更快。
- 每个成功任务成本 = 该组**全部尝试**总费用 / 成功数（含失败和摘要），0 次成功时为 N/A；缺失任一费用时总成本 N/A。
- 改进的百分点 = (新成功率 − 旧成功率)×100；相对提升 = (新−旧)/旧×100%，旧为 0 时不定义。两者不能混写。

`summarize` 当前自动提供：分组成功率、题族宏平均、逐题计数、诊断 Wilson 95% 区间、总耗时、token 总量、费用与每成功成本。阶段曲线、P90、all_success@3、配对统计需从保存的原始记录计算并复核，**当前没有自动计算这些高级指标**。

汇总器拒绝同组重复 task/seed/repeat 和重复 run_id；不同 provider/权限等没有独立字段的变化必须编码进 variant 并留在 experiment.json。它不会读实验矩阵来发现“根本没创建的运行”，也不会把尚未 start 的 run 自动归入某配置；正式出报告时必须逐项对照事先锁定矩阵核对缺失。不要把 summary.json 中较小分母误当完整实验。

## 8. 小样本与因果解释

3 次重复仍然很少；同模板的种子和同题重复高度相关。自动 Wilson 区间只是描述，独立性假设不成立时不能作显著性依据。

正式 A/B 把 task+seed+repeat 一一配对，列“双方成功/只新成功/只旧成功/双方失败”。可用 task+seed 为簇进行配对 bootstrap（每次抽一个簇连同所有重复一起抽、建议 10,000 次、固定统计 RNG seed），同时报告六个题族各自变化；只有六个题族时不要把大量物理行或 hidden test 当独立样本放大显著性。

对“只新成功”的样本检查实际日志，区分读取完整性、规则保留、工具异常恢复、代码修复和纯随机变化。要归因于压缩，至少要有发生压缩、压缩时机/内容可审计、前后配置只改压缩机制的证据。

## 9. 失败标签与复盘

一次失败可有多个诊断标签，但保留一个主要根因，并链接证据：

| 标签 | 例子 |
| --- | --- |
| coverage | 漏分片/漏配置/漏事故 |
| constraint | 修改 dev 配置、越界目录、未遵守交付 schema |
| state | 去重状态丢失、旧规则覆盖新规则、余额传播错误 |
| evidence | 草稿当确证、引用行号不对、无证据猜测 |
| code | 隐藏行为失败、异常退出、公开样例写死 |
| runtime | 工具失败后未恢复、不可恢复模型错误 |
| budget | 时间/token/工具上限触发 |
| infrastructure | 预设环境故障、provider outage，有外部证据 |

题面不清/参考答案错：暂停该题正式比较，标为 benchmark defect，修复后提升题包版本，两组同题全部重跑，保留旧记录。不允许只修评分器让一个配置变成功。

## 10. 从自建题走向可信简历证据

先报告准确措辞：“在自建的六类终端任务上……，固定模型、N 次运行……”。再选一个外部基准的预先固定子集，保持其环境、题面、评分和版本，作为外部效度补充。官方题源和许可证见 [SOURCES.md](SOURCES.md)。自建任务借鉴某个基准不等于在该基准上得分。

不要承诺“可连续工作 1 小时”直到至少有成功且日志完整的对应时长样本；不要承诺“准确率 100%”而不同时写样本数、任务范围和失败口径。简历重点是可复现的方法、你实现的机制，以及实测变化。
