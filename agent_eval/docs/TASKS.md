# 题目册与出题依据

本文件保留原六题及四个未实现扩展设计。v2 新增的 **24 个已实现题目** 见 [LONG_TASKS.md](LONG_TASKS.md)。尤其注意：旧 C01/C02 长档只扩大验收案例，不扩大模型作答上下文；旧 L01 长档只有 16 阶段。

本题包采用“先写验收和唯一规范，再反推输入与干扰项”的方法。所有数据是程序生成的虚构数据，不含真实用户信息。每题的完整可执行题面在生成后的 `workspace/PROMPT.md`；此处便于选题和理解为什么这样出。

## A01 跨分片交易对账

**情境：**一个交易平台导出了多个批次，重复消息、后续修正、作废和未入账事件混在一起。要求输出准确余额及生效事件清单。

**输入：**60 / 240 / 960 个逻辑事件，对应 6 / 24 / 96 个分片；加上重复与修订行后物理行数更多。包含不同账户和货币、0/1/99/101 分单位、重复事件和更高版本。

**作答要求：**同 ID 选最大 revision，再筛 posted；credit 加、debit 减；不换汇；零净额组合仍保留。输出 `output/reconciliation.json`，金额为整数，键为账户+币种，事件 ID 清单完整且排序。

**验收：**余额对象、ID 列表与参考值逐项相等，输入哈希不变。漏读一个分片、把旧 posted 版本重新纳入、重复记账、相差 1 分都导致该题不通过。可用脚本一次读完，效率是优点。

**对应 agent-lite：**文件遍历、搜索、完整读取、可靠命令执行；主要归因于文件操作流程和模型推理，不能仅凭这题证明上下文压缩能力。

## A02 多环境配置迁移

**情境：**把已有服务配置从毫秒迁移到秒，同时保护无需迁移的环境和版本。

**输入：**12 / 48 / 192 个配置，覆盖 prod/stage/dev、schema 1/2、目标字段已存在、嵌套字段、无关字符串中恰好出现旧字段名。另有明确标记作废的旧说明。

**作答要求：**只改 schema=1 的 prod/stage；毫秒向上取整，目标秒字段已存在时保留；删除旧毫秒字段；prod retry.count 上限 2，stage 上限 4；其他信息保留。无需迁移的文件逐字节不变。

**交付：**原地修改 eligible configs，输出包含已迁移相对路径的 `output/migration.json`。

**验收：**所有配置语义、修改清单、受保护文件哈希、新增/删除路径。把所有 `timeout_ms` 文本全局替换、误改 dev 或已为 schema 2 的文件都会失败。

**对应 agent-lite：**精确 edit、多文件范围控制、read → edit → verify 闭环；可对比同模型下工具描述/编辑策略的变化。

## A03 长日志证据核查

**情境：**旧事故汇总不可靠，需要从原始日志核对每个事故原因及损失数量。

**输入：**600 / 2,400 / 9,600 行，8 / 32 / 128 个事故查询。证据随机分布在长日志的头、中、尾，夹杂大量 heartbeat；每个事故有多个 revision，有些只有草稿没有确证。普通日志也可能含令人误判的文字。

**作答要求：**只认 `EVIDENCE ` 前缀且 confirmed 的记录，从中选最大 revision；较新的 draft 不替代确证。无确证时明确输出 null。每个结论必须引用正确物理行号。

**交付：**`output/incidents.json`，逐事故输出 root_cause、lost_records、evidence。

**验收：**全部结论与行号精确匹配；无证据回答 0、引用旧证据或混淆 draft 都不通过。日志中有大量无关材料，但不要求 agent 把全文塞入上下文。

**对应 agent-lite：**搜索、截断提示和继续取全文的能力。若 agent 使用 grep 一次取出全部证据，这次运行并未测试“截断后恢复”，应记录是否真的出现截断事件。不能把磁盘检索成绩叫作记忆能力。

## C01 事件账本修复

**情境：**一个 Python 转账处理器把所有事件直接执行，导致重复扣款、透支与乱序结果。

**输入：**错误 starter `src/main.py`、完整协议、一个公开样例和可运行的公开测试。

**作答要求：**按 ID 去重后按 (seq,id) 排序；资金不足拒绝；同账户转账记 applied 但不改变账户集合；成功的零转账也要创建账户；拒绝不创建账户；输出 balances/applied/rejected。可拆模块、加自己的测试。

**验收：**隐藏行为输入，含空输入、相同 seq、未知账户自转、拒绝、0 元、重复、随机事件。smoke / standard / long 分别 8 / 26 / 98 个新进程用例。公开样例通过只是最低门槛。

**对应 agent-lite：**从协议定位缺陷、修复与回归测试。评分器不要求固定实现或文件拆分，不按测试数量给分。

## C02 持久化任务队列

**情境：**任务可重复投递，工作进程领取租约，崩溃后要重新领取；旧执行者不能误确认新租约。

**输入：**SQLite 队列 CLI 的严格 JSON 协议、空壳程序和公开测试。

**作答要求：**实现 enqueue / claim / ack / stats；ID 幂等，正常关闭后持久化；领取按 ready_at/id 排序；精确处理 ready/lease 边界；attempt 不符或到期时拒绝 ack；done 不可重领。

**验收：**在相同 DB 上多次启动候选程序，检查 JSON 类型、payload、状态统计、重启连续性、重复投递与过期确认。三档分别为 4 / 16 / 64 个场景、8 / 32 / 128 次进程行为检查。场景数量与事务数量不是独立题目数。

**边界：**此题测试候选程序的持久化正确性，**不等于测试 agent 进程的会话恢复**。没有并发访问或强杀写事务，不得据此声称实现分布式 exactly-once 或并发线性一致性。

## L01 分阶段库存结算

**情境：**持续处理仓库批次，每阶段都要交可靠快照；业务中途更新单位规则，重复消息跨批重放。

**输入：**10 / 40 / 160 个 SKU；4 / 8 / 16 阶段，每阶段基础事件 25 / 100 / 400 条，后续另有 6 条第一阶段重复事件。全部输入不会一次发布。

**作答要求：**按数组顺序执行，库存不能负，第一次见到 ID 即计入已处理（拒绝也一样）；跨阶段重复不再执行；从阶段 3 起新事件单位乘数变成 2，此前不重算，后续继续沿用。

**交付：**每阶段独立 checkpoint，包含全量余额、本阶段 accepted/rejected、累计 processed_count、当前 multiplier。上一阶段冻结后不可改。允许保存脚本、状态、笔记，允许按正常能力恢复历史。

**验收：**评测者在发布下一阶段之前把当前答案复制到私有快照；不反馈是否正确。最终评分覆盖全部阶段，不能只在最后修对。错误输出也应正常发布下一阶段，以观察错误是否传播。

**三个协议：**normal 测正常持续工作；resume 在规定阶段间退出并恢复同一 agent 会话；compaction 确保实际压缩后再测后续结果。协议分组报告；“没有发生压缩”不纳入压缩成功样本。

**对应 agent-lite：**多轮 Agent.prompt、会话落盘/恢复、压缩后规则保留和执行持续性。默认运行允许重新读早期文件与笔记，结论是整个 harness 的恢复能力，而不是纯模型记忆保持率。

## 怎样让题真正具有长任务价值

长日志只证明材料多；运行时间长可能只是模型慢。长任务至少需要可观察的阶段依赖：早期约束影响后期，输入逐步发布，中途变化必须正确应用，产物持续累积。L01 满足这些结构，是否构成 20 分钟、1 小时的实际自主工作，由运行日志决定。

长档建议同时跑 A02、A03、C02、L01，分别覆盖大规模精确修改、长材料核查、复杂状态代码、多阶段工作。不要把这四题拼在一次会话后称为新题；如果测连续多任务会话，应事先声明每题继承哪些文件/历史，并另列协议。
