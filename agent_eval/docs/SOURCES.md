# 公开题源与取材方案

核对日期：2026-09-21。使用 TinyFish 查询并读取下列第一手资料；本文件是题源研究和适配建议，不是 agent-lite 的实测成绩。文中“建议”“适配”是本题包的设计判断。

建议先用本目录的离线自建题测出可复现的工程改进，再接入一个外部基准。agent-lite 当前的文件读写、搜索和 shell 工具适合终端任务；上下文压缩和会话持久化适合做长流程、重启恢复实验。公开基准只覆盖其中一部分。

## 选型概览

| 题源 | 主要任务 | 客观评分信号 | 适配优先级与边界 |
| --- | --- | --- | --- |
| Terminal-Bench | 在隔离环境完成复杂终端工作 | 最终状态通过验证器 | 高；最贴近文件、shell 与长流程能力 |
| SWE-bench Verified | 根据真实 issue 修改仓库 | 补丁通过规定测试 | 高；证明代码修复能力，不直接证明恢复能力 |
| LongMemEval | 从多次历史会话回答问题 | 答案正确率、检索召回 | 高；压缩和持久化的补充诊断，需按会话逐步输入 |
| τ-bench / τ²-bench | 遵守业务规则，使用工具与用户协作 | 目标状态及相关评价条件、重复成功可靠性 | 中；需要业务工具适配和用户模拟器 |
| BrowseComp | 根据多个线索持续搜索唯一答案 | 短答案正确率 | 后续；原版需要真实浏览工具，离线改题不能沿用官方成绩名 |

## 1. Terminal-Bench：优先借鉴完整工作环境和隐藏验收

官方 Terminal-Bench 2.0 仓库提供容器任务，并通过 Harbor 下载和执行。可用 `harbor run --dataset terminal-bench@2.0 --agent oracle` 检查参考解。自定义 agent 需实现 Harbor 的适配接口。[Terminal-Bench 2.0 官方仓库](https://github.com/harbor-framework/terminal-bench-2)

Harbor 把题目说明、环境、参考解和测试分开；验证器运行后写出 reward 文件。它支持多个连续步骤，适合借鉴“一个阶段完成才公布下一阶段”的出题形式。[Harbor 任务结构](https://www.harborframework.com/docs/tasks)

**适配建议：**先固定 `terminal-bench@2.0`、Harbor 版本及任务列表，用少量任务检查 agent-lite 的工作目录、超时、shell 输出和补丁导出。正式对比再固定样本扩展。自建题可借鉴“迁移数据 → 修正配置 → 恢复中断 → 校验结果”，但自行编写素材和验收器。评分应检查实际文件、服务或计算结果，而不是 agent 的“已完成”声明。

**版本和取材：**核对时官网首页已显示 Terminal-Bench 4.0；这里选择 2.0 是为了先固定明确版本，并不声称它是最新版。2.0 仓库标注 Apache-2.0；复制内容时保存对应版本许可证，并逐项核对环境中的第三方资产。只借鉴结构、自写数据最便于随题包迁移。[官方网站](https://www.tbench.ai/)、[2.0 仓库及许可证入口](https://github.com/harbor-framework/terminal-bench-2)

## 2. SWE-bench Verified：真实问题修复的外部证据

SWE-bench 的输入是仓库和 GitHub issue，输出是修复补丁；Verified 是人工确认可解的 500 题子集。官方仓库提供数据入口和容器评测工具，并提示本地评测需要较多存储与计算资源。[官方仓库](https://github.com/SWE-bench/SWE-bench)

评分器把补丁应用到指定仓库状态，在 Docker 中运行测试。应区分 resolved、unresolved、缺失提交与环境错误；命令没有崩溃不代表任务通过。修改补丁后使用新的 `run_id`，避免复用旧的缓存结果。[官方评分指南](https://www.swebench.com/SWE-bench/guides/evaluation/)

**适配建议：**先事前选定一个小子集，并保存实例 ID；agent-lite 只获得 issue 和待修复仓库，不获得参考补丁与隐藏测试。所有待比较 agent 用同一模型、预算、工具和初始提交。如果只跑子集，简历应写“在 SWE-bench Verified 的固定 N 题子集上”，不能称完整官方成绩。

**自建题取材：**选择自己拥有或允许再分发的仓库，从已修复问题构造初始状态，重写清晰需求，保留行为回归测试和正常路径测试。公共 issue 和修复可能进入模型训练，应将公开题成绩与新编保留题成绩分开。SWE-bench 工具仓库是 MIT，不能据此推定所有被测仓库都使用同一许可证。[仓库许可证与数据采集入口](https://github.com/SWE-bench/SWE-bench)

## 3. LongMemEval：验证跨会话记忆，补充压缩实验

原版 LongMemEval 提供 500 题，覆盖提取、跨会话推理、知识更新、时间推理和信息不足时拒答。官方提供历史会话、时间戳、答案和证据位置，以及用模型判断答案的脚本和检索评测脚本；这不是纯字符串匹配评分。[官方仓库](https://github.com/xiaowu0162/LongMemEval)

目前官方推荐 cleaned 数据，移除了会干扰答案正确性的历史片段；仓库也已链接到 V2。复现原版时应明确写出 cleaned 文件名和下载文件 SHA-256，避免把原版、cleaned 和 V2 混在一起。[cleaned 数据页](https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned)、[版本说明](https://github.com/xiaowu0162/LongMemEval)

**适配建议：**让历史按时间逐阶段进入 agent 会话，在指定位置触发真实压缩或进程重启，再提出需要旧信息的问题。比较正常压缩、禁用压缩、恢复会话三个条件时，保存压缩事件、恢复边界及可用输入。若把全部历史放在可 grep 的文件里，主要测的是检索，不能单凭结果宣称压缩后记忆有效。

**自建题取材：**用虚构项目决策日志编写“旧值 → 明确更新 → 后续使用”的记录，并加入不可推断的问题；用精确的 ID、日期和数值做确定性验收。下载官方数据时从输入中移除 `answer`、`has_answer`、`answer_session_ids` 等答案字段。仓库代码标注 MIT；自定义历史工具涉及 ShareGPT、UltraChat 等素材，若要再分发应分别核对数据权限，不能把代码许可证直接等同于全部对话数据的授权。[数据格式、构造方法及许可证入口](https://github.com/xiaowu0162/LongMemEval)

## 4. τ-bench / τ²-bench：准确执行规则和多次成功

τ-bench 让 agent 在业务规则和工具约束下与模拟用户对话，原始论文通过对话结束时的数据库状态与目标状态比较来评分，并提出 `pass^k` 衡量重复运行的一致成功能力。它与通常表示“k 次至少成功一次”的 `pass@k` 不同。[τ-bench 原始论文](https://arxiv.org/abs/2406.12045)

τ² 增加双方都能改变环境的 telecom 场景，检验 agent 能否指导用户完成动作，并提供可组合的任务生成思路。[τ² 原始论文](https://arxiv.org/abs/2506.07982)

**适配建议：**当前先借鉴业务规则、变更前置条件、状态对账与重复可靠性。用本地 JSON 或 SQLite 表示订单、库存、权限，每个动作具有明确前置条件；除了最终状态，还验证是否越权和重复提交。单靠最后状态相同不能证明整个过程合规。正式接入原基准则需要保留用户模拟器、业务工具与官方评价条件，文件改写版只能称自建业务流程题。

**版本和取材：**核对时旧 τ-bench 仓库已提示任务未维护，`tau2-bench` 仓库已更新为 τ³；后者还提示特定任务修正前后成绩不可直接比较。下载时固定提交、task split、用户模型和评分版本，避免只在报告中写“tau2”。仓库代码许可证为 MIT；复制时保留原许可说明。[旧仓库警告](https://github.com/sierra-research/tau-bench)、[当前维护仓库](https://github.com/sierra-research/tau2-bench)、[许可证](https://raw.githubusercontent.com/sierra-research/tau2-bench/main/LICENSE)

## 5. BrowseComp：借鉴难找、易验证的多线索题

BrowseComp 提供 1,266 道搜索题，强调答案短、明确、基本不随时间变化。官方出题思路是先找到真实答案及证据，再用多个宽泛特征反向编写线索，让发现答案困难而核验容易。[官方介绍](https://openai.com/index/browsecomp/)

官方 simple-evals 的评分实现会读取数据、解码题目和答案，再使用 grader 比较最终答案。执行时应固定代码和 grader 模型，并以已知正负答案做评分器自检。[官方评分源码](https://github.com/openai/simple-evals/blob/main/browsecomp_eval.py)

**适配建议：**agent-lite 尚未具有同等浏览配置时，优先自建“离线证据档案”：给出几十份带来源 ID 的虚构记录，要求跨文件连接，输出唯一对象、证据 ID 和约束核对表。这能检验持续搜索和精确取证，但应叫“受 BrowseComp 方法启发的离线检索题”，不叫 BrowseComp 复现。

**下载与泄漏：**官方代码中提供下载入口；官方明确请求不要把数据集题目以明文或图片公开到网上。本题包因此仅引用方法，不复制原题或答案。simple-evals 代码使用 MIT；该代码许可不取消作者对题目泄漏的明确请求，也不自动许可复制搜索所访问的网页全文。[发布页泄漏说明](https://openai.com/index/browsecomp/)、[代码许可证](https://github.com/openai/simple-evals/blob/main/LICENSE)

## 从取材到可信成绩

以下是本题包的实验设计建议：

1. 自建题先有参考解和独立验收器，再增加干扰信息、依赖链和阶段更新。通过增加真实依赖提高难度，不以无意义等待或重复读取充当“长工作”。
2. 公开练习题用于调试；保留题按题目家族拆分。仅更换随机种子不等于新任务，也不解决所有过拟合问题。
3. 题包可整体保存和迁移，但测评时只向 agent 暴露作答目录。把答案、评分代码和基准结果放在隔离的评分端；只写“禁止读取”不能构成安全隔离。
4. 固定题目版本、输入校验和、模型、agent 提交、工具、提示词、预算、网络条件与重复次数。记录失败和超时；先预定排除基础设施失败的标准，再执行实验。
5. 同时报告严格任务通过率、各类别正确率、重复成功情况、耗时和费用。完成时间长不能单独证明任务复杂；压缩或恢复收益必须有相应轨迹和消融对照。
6. 自建题成绩、官方子集成绩与完整官方成绩分别报告。没有实际运行的数据统一保持待测，不填写估计的提升百分比。
