# v2：长任务不足的分析与 24 道新增题

新增 24 个可执行入口，加上 v1 的 6 个，共 **30 个题目入口**。新增题均有生成器、完整协议、标准答案和自动验收；不是仅列标题的备选清单。M 的 8 个入口共享历史资料实验结构，R 的 6 个入口复用 W 的业务规范但改成实现任务，因此不能把它们当成 30 个统计独立能力。

## 为什么上一版可能只到 16%

用户观测：最长测试显示约 16% 上下文占用。当前目录没有提供可对应到这次测试的完整事件轨迹，无法确认这是最高值还是结束值。以下分开描述确定的设计不足与需要日志验证的解释。

**可从生成器确认的不足：**

1. A01 的大量记录可以在 Python 内聚合，只回传一个小 JSON。数据规模扩大不会按比例增加模型上下文。
2. A03 的日志可以 grep 提取 `EVIDENCE`，大量 heartbeat 无需进入模型。扩大日志主要提高磁盘检索负载。
3. C01/C02 的 long 档主要增加隐藏验收案例，它们在 agent 完成后才执行，**完全不会增加作答时的上下文**。上一版把它们叫 long 容易误导。
4. L01 的长档只有 16 阶段，业务规则主要在阶段 3 变化一次。写好通用脚本并保存少量状态后，剩下阶段很机械。它有阶段依赖，但推理和历史信息压力不足。
5. v1 没有采集每次请求的真实输入 token，也没有给“长上下文测试有效”设置单独门槛。因此功能通过不等于已经测试压缩。

**另一种必须排除的可能：**项目默认压缩后保留比例 `compact-retain=0.16`。如果 16% 是结束时的状态栏，可能在此前达到阈值并压缩后回落；这个数值巧合只能提供检查方向，不能直接断言发生过压缩。当前源码 `agent_core/agent.py` 已在工具轮次安全边界检查压缩，不能只依赖旧 README 中“用户请求开始时检查”的描述判断行为。

若本地计量窗口是 128,000，16% 对应约 20,480 token；这只是条件算术，不是本次已观测的实际输入量。物理模型窗口、configured window 和 UI 估算值也必须区分。

## 三组新题分别回答什么

| 组 | 数量 | 输入方式 | 真正增加的压力 | 不足以证明什么 |
| --- | --- | --- | --- | --- |
| M01–M08 | 8 | 同一会话逐轮直接接收新资料 | 模型必须处理的新信息；长距离证据回查；压缩后的旧规则/事实保持 | 不限制笔记，因此不是纯裸模型记忆测验 |
| W01–W10 | 10 | 隐藏未来批次，逐阶段发文件 | 多种状态机、跨批去重、事务边界、依赖传播 | 脚本可高效完成，不保证触发压缩 |
| R01–R06 | 6 | 分阶段代码实现与回归 | 每阶段源码都被冻结，旧功能必须一直有效 | 协议全部预先公开，可一次写完整实现，不保证很慢 |

长工作至少有三个轴：**执行持续时间、依赖/变更复杂度、模型实际上下文压力**。本题包把这三个轴分别记录，不奖励绕远路或高 token 消耗。更强的 agent 高效处理 W/R 是优点，不应被迫抄写无关材料。

## 规模与参数

新增题默认：

| 档位 | 阶段数 | M 每阶段新资料字符目标 | M 总资料字符目标 | W/R 每阶段基础事件 |
| --- | ---: | ---: | ---: | ---: |
| smoke | 4 | 1,800 | 7,200 | 12 |
| standard | 16 | 8,000 | 128,000 | 60 |
| long | 40 | 32,000 | 1,280,000 | 150 |

M 材料由独立记录组成，不用重复段落或随机垃圾填充。表中是**字符预算，不是 token 计数，也不是保证达到某个占用百分比**。若按 ASCII 每 token 约 4 字符做非常粗的容量预估，long 累计材料约 320k token；实际以 provider usage 为准，不能把这个估算放进成绩。

`--stages 2..128` 可覆盖 M/W/R；`--history-chars 500..64000` 仅用于 M。比如 64 阶段 × 48,000 字符约 3.07M 字符，足以进行更强压力的试跑，但费用和时间也会显著增加；不要把最大档作为第一次跑的默认选择。每个任务/参数组合和预算必须事先固定，不能某组跑不出压力就无限续题。

旧 C01/C02 的 long 仍只表示**验收覆盖规模**；旧 L01 仍为 16 阶段。新任务的 long 才是上述 40 阶段设置。

## M：需要记住“哪一条资料才算数”的八道题

完整规范和交付 schema 会写入生成后的 `workspace/PROMPT.md`、`spec/rules.md`。每轮查询要求返回实际值和资料 ID，不能仅给自然语言概括。第一阶段有后续不再更新/重复的早期锚点，后面持续抽查；另有热点对象不断发生冲突、更新和更正。

| ID | 任务 | 关键难点 | 必须拒绝的错误 |
| --- | --- | --- | --- |
| M01 | 跨月决策的最新有效版本 | 同 key 多 revision，confirmed/draft 混杂 | 最新草稿覆盖早期正式决定；忘记证据 ID |
| M02 | 历史时点与未来生效条款 | 查询的是过去时点，发布时间与生效时间不同 | 把已看到的未来条款用于过去 |
| M03 | 撤销决定与禁止旧值复活 | 最新记录明确撤销，null 也有撤销证据 | 撤销后回退到旧有效值 |
| M04 | 权威层级与较新草稿冲突 | board > owner > ops，权威优先于新旧 | 只取最新记录；低权威覆盖高权威 |
| M05 | 多条约束交集与矛盾定位 | 分 clause 选版本、撤销条款、区间交集 | 漏掉早期限制；强行把矛盾范围说成可行 |
| M06 | 跨记录引用链与循环 | 新旧映射、跨 key 引用、多跳证据、循环 | 只看直接值；循环不停；缺节点时编答案 |
| M07 | 更正与双时态追溯 | 同时限制 effective 和 recorded 时间 | 用事后到达的更正污染“当时已知”的答案 |
| M08 | 区间例外与边界命中 | 半开区间、优先级、最具体区间、版本 | end 边界算在内；宽泛条款盖过更具体例外 |

交付每阶段 `output/checkpoint-NNN.json`：

```json
{"phase":1,"answers":[{"query":{"key":"anchor-00","at":0,"known_at":1},"value":123456,"sources":["memo-001-00000"]}]}
```

这只是 schema 示例，实际值由 seed 生成。每阶段通常 6 个查询，含未知对象；M05 value 是交集对象，M06 sources 是按引用路径排列的列表，其余按各题规范。仅查询实际使用的时间字段才影响结果。

**投题必须注意：**M 的 `PROMPT.md` 只有规则，没有首轮资料。prepare 后的 `next_prompt.txt` 才是完整首轮用户消息，文件位于评测者目录；把它原文发送给同一 agent 会话。后续 checkpoint 自动更新这份文件。不要把消息改成“去读 next_prompt.txt”，也不要在 workspace 放整套历史，这会将实验变成检索题。agent 自己写笔记仍然允许，应在报告注明。

## W：十种持续变化的业务状态

每题都有初始状态和逐阶段事件，每批严格按数组顺序执行。所有事件 ID 跨阶段去重，第一次遇到即算 processed，即便被拒绝；重放返回 `duplicate`。每阶段保存全状态、逐事件结果和累计 processed_count。

| ID | 任务 | 操作与依赖 | 验收重点 |
| --- | --- | --- | --- |
| W01 | 库存预留、释放与发货 | restock/reserve/release/ship，预留和可用库存耦合 | 发货不返库存；释放才返；不足不能建预留 |
| W02 | 跨账户批次事务与回滚 | begin/post/commit/abort | 一次 commit 中后续转账失败时，前面的扣款也不能留下 |
| W03 | 依赖部署、回滚与冻结 | deploy/freeze/unfreeze/rollback | 依赖未就绪不部署；有存活下游不回滚；冻结不可变更 |
| W04 | 角色授权、继承与撤权 | allow/deny/clear/assign/revoke/check | 传递继承、deny 优先、撤权即时生效 |
| W05 | 在线字段迁移与迟到写入 | upsert/add/rename/drop | 字段变化影响全量旧行；旧 revision 拒绝；schema 和数据一致 |
| W06 | 依赖图变更与环阻塞 | add/remove/order | 全局字典序 Kahn；blocked 包括环下游，不仅环节点 |
| W07 | 多来源副本合并与墓碑 | merge/read | 版本元组比较；墓碑不能被旧副本复活；null 与不存在的处理 |
| W08 | 多租户配额和周期切换 | consume/limit/refund/reset | 降额度不改已用量；过期 reset 不清零；拒绝消息不重放 |
| W09 | 构建依赖失效与增量重建 | change/build | 传递失效；依赖仍 dirty 时不可 build；不能自动重建未要求节点 |
| W10 | 工单时钟、暂停与重开 | open/tick/pause/resume/close/reopen/report | 暂停不耗时；重开不赠送预算；精确检查逾期边界 |

这些题可快速写成脚本。它们用于发现状态维护、规则执行和长流程工作错误，**不会因占用低就算失败**。若要专门测压缩，请优先选择 M，或给 W/R 预先声明压力门槛并如实报告未达到。

## R：每阶段都要能工作的六道实现题

R01–R06 分别对应 W01–W06 的业务规则，但需要实现一个可执行的 `src/main.py`：stdin 接收 `{initial,batches}`，stdout 返回各批 checkpoint 数组。每次进程独立，使用输入给定的 initial 从头执行。

- 阶段从较少操作组合开始，随后纳入更多操作与旧批次重放。完整操作语义预先公开，不人为隐藏必要规范。
- checkpoint 时同时冻结源码；阶段 1 的错误实现不能靠阶段 40 的好代码替换后再评分。
- 每阶段都有公开历史回放和独立随机隐藏回归两个案例；隐藏输入不会进入 agent 的上下文。
- 每阶段必须输出正确 checkpoint，同时源码在当时的行为测试通过。只交一份计算正确的 JSON、代码仍是空壳，不能通过。
- 长档 40 阶段意味着 40 份源码快照、80 组代码行为验收；这些不是 80 道独立题。

R 可以测“早期实现→边界暴露→修改→回归”的过程，但完整实现也可能很快完成。更复杂的真实代码库迁移仍可按旧 [扩展题设计](TASKS.md) X01–X04 后续接入，不能用生成的事件数量代替真实工程复杂度。

## 怎么选择第一轮任务

1. **M03 long**：先核对峰值、真实压缩次数和撤销后的旧值复活错误。
2. **M07 long**：增加历史时点与迟到更正的区分。
3. **W02 long**：检查长流程中原子事务和重复事件处理。
4. **R04 standard 或 long**：检查传递权限、撤权和多轮源码回归。

先用每题 1 seed、1 repeat 校准，不必一上来把 30 题 × 多种子全部跑完。低压力时记录“功能完成，压力未达标”，再**在下一轮独立实验**提高 stages/history-chars 或改为预先固定的小窗口压缩实验。

## 通过条件和压力条件分开

`autonomous_success` 沿用功能正确、时限、人工帮助等判断。新增：

- `pressure.peak_measured_ratio`：主模型请求中 provider 返回 input_tokens / 声明窗口的最大值。
- `last_measured_ratio`：最后一次主请求占比；可与峰值显著不同。
- `successful_compactions`、`fallback_compactions`：观测到的压缩成功及机械兜底次数。
- `post_last_compaction_stage_pass_rate`：最后一次压缩所在阶段之后，已评分阶段的正确比例；没有后续完整阶段时 null。
- `longest_correct_stage_prefix`：从阶段 1 开始连续正确的阶段数。
- `pressure_qualified_success`：功能成功、预先设置的峰值/压缩门槛都满足；要求压缩时还必须有至少一个压缩后的已评分阶段。

估算事件、provider 主请求、摘要请求分别记录；不能用摘要模型输入或累计计费输入冒充工作上下文峰值。无 usage/events 时压力状态为未知，不是 0，也不是通过。`context_window` 是声明的本地计量分母，必须与实验配置一致，不能为了提高百分比虚报窗口。

建议主压力实验提前设 `--min-peak-ratio 0.75 --min-compactions 2`。这不是普适正确阈值：自动压缩可能在 provider 请求前触发，导致观测主请求峰值略低于触发阈值。应同时保留本地估算触发点，先校准一次，再固定门槛。

## 自动投题和记录（需你主动执行，实际调用模型）

在 `agent_eval/` 下：

```text
python eval.py prepare --task M03 --seed 17017 --scale long --out runs/m03-long-r1
python run_agent_lite.py --run runs/m03-long-r1 --repo-root "D:\project space\agent lite" --model MODEL_ID --sandbox wsl --variant current-pressure --budget-seconds 7200 --context-window 128000 --protocol compaction --min-peak-ratio 0.75 --min-compactions 2
python eval.py grade --run runs/m03-long-r1
python pressure.py --run runs/m03-long-r1
```

自动适配器负责 start、同一会话多阶段投题、冻结结果、finish，不要提前手动 start。它按事件和逐次 provider usage 记录 `events.jsonl`，包括独立摘要 provider；保留 `adapter.json`、原会话、stdout/stderr。未拿到 usage 的调用使累计 token 为 null；中断后也不声称完整成本。成本仍需根据真实价格和缓存分类计算。

R 题完成后需要额外 `grade --execute-submission`，在隔离评测环境执行源码。其他 agent 可由评测者原样发送 `next_prompt.txt` 并手动 checkpoint，或者编写同契约适配器；未来资料和答案仍只由评测者持有。

适配器会真正调用已配置的模型；本次交付没有发起真实长上下文付费运行。已通过离线模拟的单会话投题和 usage 采集测试，不代表真实 provider、网络和沙箱组合都已端到端验证。

父进程设置总墙钟超时并终止 worker；它不提供完整的进程树/内存/磁盘/网络隔离，仍需要外围 VM/容器。当前适配器支持 normal/compaction；resume 仍按原方案人工重启并记录，不能把源码快照测试误称 agent 重启测试。自动工具批准只应在准备好的评测环境内使用。

## 单独核查“16%”

有原 session 文件时：

```text
python pressure.py --session PATH_TO_SESSION.json --context-window 128000
```

这只能给出末态估算及已持久化压缩条目数量，**不能还原历史峰值**。有 events.jsonl 才能区分“峰值一直很低”和“高峰后已压缩”。不要把 sessions JSON 文件大小当作输入 token；里面可能保留已压缩历史、工具结果和显示用 reasoning。

## 如何写结果

可写：“在【固定模型/128k 本地窗口】的【N】次历史资料多阶段任务中，观测到主请求最高【x】token，至少两次压缩后完整交付【s/N】次。”同时列出未达压力门槛的样本，不从分母悄悄删掉。

不能写：“已支持 128k/百万 token 工作”，仅因为累计资料达到该规模；不能把这次离线参考解自测写成 agent 实测成功率。新版应与 v1 分开报，版本是 2.0.0。
